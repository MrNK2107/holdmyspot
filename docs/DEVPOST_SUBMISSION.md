## Inspiration

Solo appointment pros (nail techs, barbers, lash artists, tutors) lose a slot's income to every no-show. At nail studios about 1 booking in 25 is a no-show and 1 in 9 is cancelled, on a $73 median ticket (Zenoti, 2026 Beauty & Wellness Benchmark Report, summarised at https://www.zenoti.com/thecheckin/no-show-revenue-calculator). Enforcing their own cancellation policy is awkward: charging a regular feels unfair, and when they do try, the card on file declines after the fact. When fees are enforced, it is often rigid: a client charged after their child got sick. We wanted the owner to get guaranteed funds *and* judgment: hold the fee before the visit, read the client's reason the way a person would, and try to refill the slot first so most late cancellations end with nobody losing.

## What it does

- **Policy in your own words.** The owner pastes the cancellation policy they already text clients. The AI compiles it into typed rules and asks about the gaps ("Does a sick child count as an emergency?"). The owner answers and approves; rules are versioned and hashed, and the client-facing summary is generated by code from the approved rules.
- **A PayPal hold, not a deposit.** Clients book from a mobile booking page and approve PayPal once. Visits within 72 hours get an authorization right away; later visits save the PayPal wallet (Vault) and the engine places a merchant-initiated authorization 72 hours before the visit. A decline is caught three days early, with a re-approval link, not at the door.
- **Reads "can't make it" texts.** The AI labels each message (intent, reason, confidence, evidence span). A deterministic policy engine decides what happens: release the hold, refill first, or ask the owner.
- **Refill first, fee last.** A late cancel offers the slot to the top three matching waitlisters. The slot is only filled once the claimer's own PayPal hold authorizes; if their hold declines, the next person gets it. If it fills, the canceller's authorization is voided: "Late cancel. $0 lost. $0 charged."
- **The owner always taps before money moves.** No-shows and unfilled late cancels produce a capture card; one tap captures the fee from the existing authorization. Refund is one more tap. Silence never charges.
- **An agent you can inspect.** Each client text runs the front desk as a tool-calling agent: `get_booking`, `get_policy` (read only), `classify_message` (label only), `propose_settlement` (a proposal to the policy engine). The **Agent trace** tab shows every call with its arguments and result, the policy check it triggered and the money gate: released automatically, refill first, or waiting for the owner. There is no capture, void, refund or authorize tool; a request for one is logged as denied. The owner's tap and the PayPal call it caused are added to the same run.
- **The owner can ask it too.** "How did this week go?" is answered from `list_transactions`; "Alex apologised, refund her fee" makes the agent find the capture and `propose_refund`, which appears as a Refund / Keep card. Only the owner's tap sends the PayPal refund.
- **Money ledger (AG Grid).** One row per booking with its money state, held / charged / refunded amounts and the PayPal authorization, capture and refund ids, plus a totals row; a second view lists every PayPal API call and webhook. Search, filters, CSV export. A third view shows the exact REST request behind each simulated step (method, sandbox URL, `PayPal-Request-Id`, JSON body), built by the real PayPal adapter against a capturing fetch, so the payloads can be checked without keys.
- **Money timeline.** Every booking shows its audit log: AI outputs, engine decisions, PayPal calls and webhooks.

## How we built it

- **TypeScript end to end.** Fastify API with server-sent events; React + Vite owner console and booking page; vitest.
- **Engine** (`server/src/engine/engine.ts`): a booking state machine (BOOKED → VAULTED → HELD → PENDING_REFILL → REFILLED / CHARGED / EXCUSED …), a pure `decide()` policy function, and capture invariants (capture ≤ authorized, ≤ policy maximum, never on emergency/medical/bereavement without the owner, never without an owner tap). It is the only code that calls the payments gateway.
- **Payments gateway interface** with two adapters: the real PayPal REST adapter, and a deterministic sandbox simulator that models PayPal's rules (3-day honor period, 29-day validity, one reauthorization, capture ≤ authorized, idempotency by `PayPal-Request-Id`, negative-testing declines, async webhooks).
- **AI front desk** behind a provider interface: Claude through the Anthropic API with structured outputs, plus a deterministic offline provider for tests and keyless demos. The agent loop (`server/src/ai/agent.ts`) gets its tools from the engine per message as plain functions; a test fails the build if any AI module imports the payments or engine code, and agent tests check that a model asking only for money tools moves no money.
- **Ledger:** AG Grid Community (`ag-grid-react`), lazy-loaded so the console stays light.
- **Hosting:** a Render Blueprint (`render.yaml`, one free web service, keyless by default; a test checks it against the real scripts and health route).
- **Testing:** 253 automated tests, including end-to-end tests that drive a real HTTP server through all three hero flows and both failure paths, and a headless-browser check (`npm run ui-check`) that plays the guided demo, runs axe accessibility checks (0 violations on 14 screens, including the agent trace and the AG Grid ledger at 390 px) and refreshes the screenshots.
- **Guided demo:** `npm run demo` starts a seeded studio with a scripted clock; 13 beats show the whole week in under three minutes.

## PayPal APIs used

| API | Where |
|---|---|
| Orders v2, `intent=AUTHORIZE` (buyer-present, `store_in_vault: ON_SUCCESS`) | Booking within 72 hours; re-approval link after a decline; refill claims from clients without a saved wallet |
| Orders v2 with `vault_id` + `stored_credential` (merchant-initiated) | The T−72h hold on a saved wallet |
| Vault v3 setup tokens → payment tokens | Bookings more than 72 hours out: save the wallet now, hold later |
| Payments v2: void authorization | Excused cancellations, refilled slots, clients who showed up |
| Payments v2: capture authorization (`final_capture`) | No-show / unfilled late-cancel fee, after the owner's tap |
| Payments v2: reauthorize | Capturing after the 3-day honor period |
| Payments v2: refund capture | The owner relents |
| Webhooks + `verify-webhook-signature` | `PAYMENT.AUTHORIZATION.CREATED` etc., deduplicated and routed by `custom_id`; the endpoint refuses events when verification is not configured |
| `PayPal-Request-Id` on every write | Idempotent retries keyed to the business intent |
| **PayPal Agent Toolkit** (`@paypal/agent-toolkit` 1.11.0): `list_transactions` (Transaction Search), `get_order`, `get_refund`, `list_disputes`, `get_dispute` | The owner's agent reads PayPal with the official toolkit, read-only by allow-list; optionally through the toolkit's MCP server class (`PAYPAL_AGENT_TOOLKIT=mcp`). Its money tools are never given (see How we used AI) |

## How we used AI

- **Model:** Claude (Anthropic API, `claude-sonnet-5-5`), structured outputs. [TODO confirm the model actually used for the final run]
- **Five jobs:** run the front desk agent (choose the next tool for each client text); compile the owner's prose policy into rules + clarifying questions; classify client messages (intent, reason, confidence, evidence span); parse free-text waitlist wishes and rank eligible candidates; draft the friendly replies.
- **PayPal Agent Toolkit, read only:** when the owner asks ("Alex apologised, refund her"), the agent confirms the capture on PayPal with the toolkit's `list_transactions` before it proposes the refund card. It gets five toolkit read tools and none of the toolkit's money tools (`create_refund`, `pay_order`, `create_order`, `accept_dispute_claim`). We found that the toolkit's own `handleToolCall` dispatches any tool name even when the configuration leaves it out, so we added two gates: a wrapper that refuses names outside the allow-list, and an HTTP gate that lets only GET requests out. A test has a model ask for every toolkit money tool: all denied, no money moved. Tested against the simulator only; not yet against the live sandbox.
- **Where we refused to use AI:** money. The model never sees an amount, an authorization or a PayPal parameter in its output schema, and the agent's tools can read and propose but never move money. It proposes a label; the engine decides; the owner taps. Waitlist eligibility is a deterministic filter; the model only ranks the filtered list. The client-facing policy summary is generated by code.
- **Evaluation:** `npm run eval` measures the message reader (macro-F1, cost-weighted wrongful-charge errors, abstain rate), the money effect of prompt-injection messages through the real engine (0 so far), and the waitlist matcher. ## Challenges we ran into

- **Authorizations expire on a schedule.** PayPal's honor period is 3 days and an authorization lives 29 days, so a hold placed at booking for a visit two weeks out would be stale. We save the wallet at booking and place a merchant-initiated hold at T−72h, with reauthorize as the fallback, and model both in the simulator.
- **A refill is only real when money is.** The first version filled the slot when someone texted "yes". Now the slot fills only when the claimer's own authorization succeeds; a declined claimer passes it on to the next person, and a claim still pending at the slot's start is closed.
- **Late events.** Webhooks and buyer approvals can arrive after a booking was cancelled. The engine voids any authorization that shows up for a finished booking and ignores stale or duplicate events.
- **A late cancel with no hold yet** (wallet never approved) used to just free the slot. It now follows the same refill-first path, and if nobody claims it the fee is waived automatically, because there is nothing to capture.
- **Money review.** An independent review of the money engine found 11 bugs (refunds above the captured amount, double reauthorization, retry keys per attempt instead of per intent, …); each is fixed with a regression test.
- **Adversarial money review.** A second, adversarial pass read the engine as an attacker and as an unlucky owner would, and found 26 more money-state bugs: an owner card left open after the booking moved on could void a hold; a fee could be computed from a policy the client never agreed to; a webhook could interleave with an owner tap; a capture PayPal later reversed still showed as collected; a charge after the 29-day authorization expiry failed on every tap; one workspace's owner questions could read another's sandbox transactions. Every one was reproduced with a failing test first, then fixed, so each is now a regression test. We count that as a strength: the money paths are the part most worth attacking, and they have been.

## Accomplishments we're proud of

- "Late cancel. $0 lost. $0 charged." works end to end, including the declined claimer.
- The AI cannot move money, by construction and by test.
- The whole week plays in under three minutes, from one command, with no keys.

## What we learned

Authorizations, not deposits, are the right primitive for no-show protection: they cost the client nothing when things go well, and void, partial capture and reauthorize map directly onto fair outcomes. And the most useful AI feature was reading reasons, not deciding charges.
